1 Introduction 
1.1 Purpose 
This document specifies the software requirements for the development of an Online Shopping 
System (OSS), a web-based e-commerce platform intended to enable customers to browse products, 
place orders, and make payments online, while allowing administrators and vendors to manage 
inventory, orders, and sales operations. This Software Requirements Specification (SRS) describes the 
functional and non-functional requirements for Version 1.0 of the system and is intended to serve as 
the primary reference for the design, development, testing, and acceptance of the product. 
This document follows the structure recommended by IEEE Std 830-1998, “IEEE Recommended 
Practice for Software Requirements Specifications.” It is written for use by the development team, 
project stakeholders, quality assurance personnel, and academic evaluators reviewing the project. 
1.2 Document Conventions 
• Requirement identifiers follow the pattern FR-XX for functional requirements and NFR-XX 
for non-functional requirements. 
• Priority levels are classified as High, Medium, or Low, indicating the criticality of the 
requirement to the Minimum Viable Product (MVP). 
• The keywords shall, should, and may are used per IEEE convention: shall denotes a 
mandatory requirement, should denotes a recommended requirement, and may denotes an 
optional requirement. 
• Terms defined in the Glossary (Appendix A) are italicized on first use within a section. 
1.3 Intended Audience and Reading Suggestions 
• Developers — should read Chapters 3, 4, and 5 in detail for implementation guidance. 
• Project Evaluators / Reviewers — should read Chapters 1, 2, and 4 to assess scope and 
functional coverage. 
• Testers / QA — should focus on Chapter 4 (System Features) and Chapter 5 (Non-Functional 
Requirements) to derive test cases. 
• Project Managers — should read Chapter 2 for scope and Chapter 6 for outstanding items. 
Readers unfamiliar with domain-specific terminology should first consult the Glossary in Appendix 
A. 
1.4 Product Scope 
The Online Shopping System (OSS) is a centralized, role-based web application designed to manage 
the complete lifecycle of an online retail operation. The system shall support three primary user roles: 
Administrator, Vendor/Seller, and Customer, each with a distinct set of permissions and dashboards. 
The core objectives of the OSS are to: 
• Eliminate manual, in-person or phone-based ordering processes for retail purchases. 
• Provide customers with a self-service platform to browse products, manage a shopping cart, 
and complete purchases securely. 
• Provide vendors with tools to list products, manage inventory, and fulfill orders efficiently. 
• Provide administrators with a consolidated view of sales, inventory, and customer data for 
reporting and decision-making.

2 Overall Description 
2.1 Product Perspective 
The OSS is a new, self-contained software product. It is not a modification of an existing system, 
although it may later be integrated with third-party services such as payment gateways, 
shipping/courier APIs, or SMS/email gateways for order notifications. 
The system follows a three-tier architecture: 
• Presentation Tier: A responsive single-page web application (SPA) providing role-specific 
dashboards (Customer storefront, Vendor console, Admin panel). 
• Application/Logic Tier: A RESTful API server responsible for business logic, 
authentication, authorization, cart/order processing, and payment orchestration. 
• Data Tier: A NoSQL document database responsible for persistent storage of all catalog, 
order, and account data. 
2.2 Product Functions 
• User authentication and role-based access control. 
• Product catalog and inventory management. 
• Shopping cart and wishlist management. 
• Order placement, checkout, and payment processing. 
• Order tracking and fulfillment management. 
• Product reviews and ratings. 
• Discount, coupon, and promotion management. 
• Notifications (order confirmation, shipping updates). 
• Reporting and analytics (sales, inventory, customer behavior).

2.4 Operating Environment 
• Client side: Modern web browsers (Chrome, Firefox, Edge, Safari — latest two major 
versions), supporting both desktop and mobile viewports. 
• Server side: Node.js runtime (LTS version) running an Express.js application server, 
deployable on Linux-based cloud infrastructure. 
• Database: MongoDB (self-hosted or Atlas-hosted cluster). 
• Network: HTTPS over the public internet. 
2.5 Design and Implementation Constraints 
• The system shall be implemented using JavaScript/TypeScript across both frontend and 
backend to maintain a unified codebase and skill set. 
• Authentication shall be implemented using stateless JSON Web Tokens (JWT) rather than 
server-side sessions, to support horizontal scalability. 
• The database schema shall be document-oriented (MongoDB), which constrains the system to 
eventual-consistency patterns for certain cross-collection aggregate operations (e.g., platform-
wide sales reports). 
• The system must be deployable on infrastructure with modest resources (minimum 2 vCPU / 
4GB RAM) to remain viable for small-to-medium retailers. 
• All passwords must be stored using a salted one-way hashing algorithm (bcrypt or 
equivalent); plaintext password storage is strictly prohibited. 
• Payment card data shall never be stored directly by the system; all card transactions shall be 
delegated to a PCI-DSS compliant third-party payment gateway. 
2.6 User Documentation 
• A User Manual covering role-specific workflows for Administrators, Vendors, and 
Customers. 
• An API reference document (auto-generated where feasible) for developers integrating with 
the system. 
• An in-application onboarding/help tooltip system for first-time users. 
2.7 Assumptions and Dependencies 
• It is assumed that end users have access to a stable internet connection and a modern web 
browser.

3 External Interface Requirements 
3.1 User Interfaces 
• The system shall provide three distinct dashboard layouts corresponding to the Administrator, 
Vendor, and Customer roles. 
• All interfaces shall be responsive and usable on screen widths from 360px (mobile) to 1920px 
(desktop). 
• Form validation errors shall be displayed inline, adjacent to the relevant field, within 200ms 
of user input where client-side validation applies. 
• The system shall provide breadcrumb navigation for any workflow nested more than two 
levels deep. 
• The system shall provide a persistent shopping cart indicator visible from any page in the 
customer storefront. 
3.2 Hardware Interfaces 
The system does not directly interface with specialized hardware. Standard peripherals (keyboard, 
mouse, touchscreen) are assumed for client interaction. No barcode scanners or POS terminals are 
required for Version 1.0, though such integrations are identified as future enhancements (see 
Appendix C).

4 System Features 
This chapter enumerates the functional requirements of the OSS, organized by feature area. Each 
feature includes a description, priority, and a table of associated functional requirements. 
4.1 User Authentication and Access Control 
4.1.1 Description and Priority 
High Priority. Provides secure registration, login, logout, and session management for all user roles, 
along with role-based authorization for all protected resources. 
4.1.2 Stimulus/Response Sequences 
• User submits registration or login credentials (email/username and password). 
• System verifies credentials, issues a signed JWT, and enforces role-based access on 
subsequent requests. 
4.1.3 Functional Requirements

FR-04 The system shall reject access to any protected API endpoint when a valid JWT is not supplied in the request header. High 
FR-05

endpoint access according to the user’s assigned role (Admin, Vendor, 
Customer).

5.2 Safety Requirements 
The system does not control physical machinery or safety-critical infrastructure. However, it shall 
implement safeguards against accidental irreversible data loss: all deletions of catalog and order 
records (products, orders, customer accounts) shall be implemented as soft deletes, with a recovery 
window of 30 days before permanent purging. 
5.3 Security Requirements 
ID Requirement 
NFR-04 All user passwords shall be hashed using bcrypt (or equivalent) with a minimum cost factor of 10 before storage. 
NFR-05 All communication between client and server shall be encrypted using TLS 1.2 or higher.  
NFR-06 JWT access tokens shall expire within 24 hours; refresh tokens, where implemented, shall be revocable server-side. 
NFR-07 The system shall sanitize all user inputs to prevent injection attacks (NoSQL injection, XSS), consistent with OWASP Top Ten guidance. 
NFR-08 The system shall never store raw payment card data; all payment processing shall be delegated to a PCI-DSS compliant gateway. 
NFR-09 The system shall log all administrative and vendor actions (product deletion, order status override, refund issuance) to an immutable audit trail. 
 
5.4 Software Quality Attributes 
• Availability: The system shall target 99.5% uptime, excluding scheduled maintenance 
windows. 
• Maintainability: The codebase shall follow a modular structure (separated routes, 
controllers, models) to facilitate independent module updates. 
• Usability: A first-time user shall be able to complete a core task (e.g., adding a product to the 
cart) without external instruction, within 3 interactions. 
• Portability: The backend shall be containerizable (Docker) to support deployment across 
differing hosting environments. 
• Scalability: The stateless authentication design shall permit horizontal scaling of the 
application server tier behind a load balancer, especially during high-traffic sales events. 
5.5 Business Rules 
• Only an Administrator may create or deactivate vendor accounts. 
• A Vendor may only manage products and orders associated with their own catalog. 
• A Customer may only view (not modify) order status once an order has been confirmed, 
except to request cancellation or return. 
• Confirmed orders are immutable except via an explicit, logged Administrator or Vendor 
override (e.g., cancellation, refund).

6 Other Requirements 
6.1 Data Retention 
Transactional records (orders, payments, invoices) shall be retained for a minimum of 7 years 
following order completion, in accordance with typical financial record-keeping and tax regulations. 
6.2 Legal and Compliance 
The system shall be designed to accommodate applicable data protection principles (e.g., limiting 
collection of personally identifiable information to what is operationally necessary, providing 
mechanisms for data correction upon request) and shall support PCI-DSS compliant payment 
handling practices. 
6.3 Internationalization 
Version 1.0 shall support the English language and a single currency only. The architecture should not 
preclude the addition of multi-language and multi-currency support in future versions. 
 
7 Appendix A: Glossary 
Term Definition 
OSS Online Shopping System — the software product specified in this document.

RBAC Role-Based Access Control; an authorization model restricting system access based on user roles. 
SKU Stock Keeping Unit; a unique identifier assigned to a distinct product/variant.

Cart A temporary collection of products selected by a customer prior to checkout. 
Coupon A code entitling the bearer to a discount on an order, subject to defined validity rules.

B.3 Use Case Specification: Checkout and Payment 
Field Description 
Use Case ID UC-04 
Name Checkout and Payment 
Actor Customer 
Precondition Customer is logged in and has at least one item in their cart. 
Main Flow 
1. Customer reviews cart contents and proceeds to checkout. 2. System displays 
shipping address and shipping method options. 3. Customer selects/enters 
shipping details. 4. Customer proceeds to payment and selects a payment method. 
5. System validates stock availability for all cart items, then redirects to the 
payment gateway. 6. Upon successful payment confirmation, the system creates 
the order record and clears the cart. 
Alternate Flow If any cart item is out of stock at validation time, the system displays an error and prompts the Customer to adjust the cart before proceeding. 
Postcondition Order record is persisted with status “Confirmed”; stock levels are decremented; order confirmation notification is dispatched.
